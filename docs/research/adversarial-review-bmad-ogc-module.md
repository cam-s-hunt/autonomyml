## (a) Verdict

R2's core guidance survives. The BMAD half is accurate and unusually well verified. I re-ran BMAD's `validate_manifests.py` against the R2 sketch and against the proposal's invented tables and got the results R2 reports. The conclusion that `bmod.toml` is a packaging manifest that cannot execute, require or enforce anything is correct on the evidence. The ModSpec rule correction (recommendations and permissions are not tested) is correct against r7 and also against r3, so the proposal's linter rule is wrong either way.

Three things should change before anyone builds from it.

1. **The CI gate recipe in R2 would not work as written.** It fails on "any `MODSPEC_*` message whose subject is a requirement, class or test". By R2's own source reading, Metanorma emits `MODSPEC_2` for any `inherit`/dependency target that is not in the same document. AutonomyML will depend on CS API and SensorML, so it will have such targets. Its severity settings contradict each other (config default 2, CI text 0 or 1, OGC header checks all severity 2). Its "known-good fixtures" calibration cannot return "no findings" on the proposed fixtures. One of the invariants it lists (Req 1) is mis-cited, and the "exactly one class" rule needs a deliberate reading. The gate needs an explicit rule table with IDs and positive and negative fixtures, not a severity threshold.
2. **The architecture is right but under-specified, and one of its stated reasons is weak.** The sketch puts a gate in the module (`ogcspec-gate/scripts/gate.py`) and another in the standard repository (`tools/gate/`) without saying which is the source of truth. Nothing prevents drift. The real justification for a BMAD-independent gate is OGC 05-020r29's rule that SWG deliverables live in an OGC-controlled environment, not the 26-021 discussion paper that R2 leans on. A design R2 did not consider also fits the user's paradigm: the module ships the gate as a declared script, and both CI and `bmad-loop` call that one copy. R2 also missed that the Naming Authority reviews the repository, not just the document, which bears directly on the YAML-versus-AsciiDoc question it leaves "open".
3. **Governance is partly overread and partly incomplete.** The "private BMAD pipeline" sentence conflates the text repository with the tooling repository. R2 does not mention the repository's licence (the repo's `LICENSE` is the Start Bootstrap website-template MIT licence, copyright 2013-2021), the mandatory OGC copyright statement, repository migration at SWG formation, or the licence terms for shipping r7 text inside a public skill. It also stays silent on a draft OGC ModSpec Policy (25-001, sitting unread in the local `ogc-modspec` clone) that mandates ISO/IEC Directives Part 2 verbal forms. That contradicts the "RFC 2119 keyword" lens R0 recommended and R2 leaves in force.

The sequencing advice (build the portable pieces first, package the `bmod.toml` after v7 releases) is sound. It is weaker than it looks because the ETA is days away, and R2 never asks whether packaging as a module beats repo-local skills for a single-repo project.

R2 also has a number of smaller defects: misdescribed study statistics, a mis-applied ModSpec citation in M12, a verdict count that depends on how rows were merged, "does not exist" where its notes say "not found", and a sketch that keeps a question R2 itself calls meaningless.

## (b) Findings, ranked by whether they change what gets built

### F1 (High). The CI gate recipe rejects conformant documents and its calibration step cannot pass

Location: R2 "Corrected module skeleton", last paragraph (CI step and calibration step); the `max_log_severity` question in the bmod.toml sketch; table rows M4, M13.

Claims quoted:
- "fail on any severity 0 or 1 message and any `MODSPEC_*` message whose subject is a requirement, class or test, while exempting recommendations and permissions."
- "the OGC flavor's own validators, whose messages are all severity 2, so the severity threshold, not the exit code, decides whether a malformed header blocks the merge."
- "run the gate over the published `ogc-modspec` and CS API sources as known-good fixtures and confirm it produces no findings on them."
- Sketch: `key = "max_log_severity"`, prompt "Fail the gate ... at this severity or lower", `default = "2"`.

Problems:
1. **MODSPEC_2 false positives.** `Modspec#reqt_to_dependency` logs `MODSPEC_2` whenever an `inherit`, `indirect-dependency` or `implements` target is not found among the same document's labels (`mn-requirements/lib/metanorma/modspec/validate.rb`, `reqt_to_dependency`, and `log.rb` for the message). CS API's own sources inherit external classes, for example `inherit:: http://www.opengis.net/spec/ogcapi-1/1.0/conf/core` (cited in N-MN Q2). AutonomyML's stated design rests on CS API and SensorML, so a "fail on any MODSPEC_* about a requirement, class or test" rule fires on every cross-standard dependency. R2 never mentions MODSPEC_2's external-target behaviour even though it quotes the message table in the notes.
2. **Contradictory thresholds.** The CI text says fail at severity 0 or 1. The config default says fail at 2 or lower. The same paragraph says the OGC-flavor header checks are all severity 2 (I confirmed 18 of 18 in `metanorma-ogc/lib/metanorma/ogc/log.rb`). A threshold of 1 therefore never blocks a malformed header, and a threshold of 2 also catches MODSPEC_1 for recommendations and permissions, MODSPEC_2 for external targets, and 17 other severity-2 standoc messages (counted in `metanorma-standoc/lib/metanorma/converter/log.rb`). Severity is the wrong control surface. The gate needs an allow-list or deny-list by message ID plus element classification.
3. **Log lines do not label recommendations and permissions.** `CLASS2LABEL` renders all three as "Requirement" because they share `type: general`. The message does carry the identifier, so a `/rec/` or `/per/` prefix could be used as a convention to exempt them, but that is fragile (it depends on authors following the prefix convention). Semantic XML, classified by element name, is the sturdier input. R2 says "log or XML" without noting the difference.
4. **The calibration fixtures cannot be clean.** `ogc-modspec` itself contains 5 `[recommendation]` and 8 `[permission]` blocks (ids such as `/rec/core/uri-external-use`, `/per/core/repeated-requirements`). I grepped all of `sources/` (excluding the `recommendations/` and `permissions/` folders and generated html/xml/pdf) for each of the 13 identifiers: 12 appear nowhere else, and one (`/rec/core/uri-external-use`) appears only in the informative user guide; none appears in `abstract_tests/`. So none is targeted by a test. If R2's code reading of MODSPEC_1 is right (it is the same reading, not independent evidence), Metanorma would warn on all 13 when compiling OGC's own ModSpec; that is a prediction to test, not a confirmation. CS API Part 1 has no Core requirements class (R0/R1 carry this as "uninvestigated") and uses external `inherit`. "No findings" is unreachable. Calibration must be differential: record a baseline of expected findings per fixture and fail on deviation.
5. **Mis-cited and contested invariants.** R2 says "every requirement is tested (Req 1)". r7 Req 1 (`/req/core/reqs-are-testable`) says "All the parts of a requirement SHALL be testable" and that failure of a part is a failure of the test. The requirement-to-test coverage comes from Req 15 (a conformance class SHALL test all requirements of its requirements class) read with Req 8 and Req 9 (08-131r7 text, local `dl/08-131r7.txt` lines 379-388, 535-548). R2 also lists Req 28 (each requirement in exactly one class) as a fatal check. That is a defensible reading, but note the surrounding r7 text: line 547 says a requirement "should be contained explicitly in one and only one requirements class ... This is not really a requirement here, since a single requirement can be stated twice in different requirements classes with different standardization target types", and Permission `/per/core/repeated-requirements` allows repeating a requirement word for word in another requirement. A check keyed on identifiers (each identifier belongs to one class) is compatible with both, because a repeated statement carries its own identifier; a check keyed on statement text would not be. R2 should say which it means. The numbering in r7 is also internally inconsistent ("Requirement 1-28" label; A.15 and A.28 name different tests for the same idea).
6. **M12 misapplies Req 28.** R2 says a global `/req/model/` prefix "puts every requirement in one class, against Req 28". One class containing everything satisfies "exactly one class". The actual violations are Req 4 (single standardization target type per class), Req 6/7 (grouping that parallels conformance classes) and Req 20 (separate core class). The correction in the table is still right; the stated reason is wrong.

Evidence: files cited above; `scratchpad/ogc-extra/mn-requirements` HEAD is tag v0.5.15 (single-commit shallow clone, `git tag` shows v0.5.15, `VERSION = "0.5.15"`), so the code I read is the released version. `metanorma-standoc` HEAD is v3.5.11 and `metanorma-cli` is v1.18.4. `metanorma-ogc` and `metanorma` HEAD are untagged, so the OGC-flavour message table may be ahead of the released gem.

Fix: replace the severity threshold with a rule table. Each rule has an ID, an input (semantic XML element set), a pass/fail test, a source clause, and a positive and negative fixture. Treat MODSPEC_2 as a finding only for targets that should resolve inside the document; for external targets check syntax and a declared normative-reference list. Re-cite Req 15 for requirement-to-test coverage. Decide Req 28 deliberately and note PER003. Make calibration differential.

### F2 (High). "Pipeline lives in CI, module is thin" is justified, but the sketch leaves the gate duplicated and one stated reason is weak; a stronger design was not considered

Location: R2 "A bmod.toml packages skills; the pipeline must live in CI"; layer table; skeleton; Conclusion; "OGC 26-021" sentence in the governance section.

Claims quoted: "the authoritative validation pipeline lives in repository CI and stays BMAD-independent; a thin BMAD module packages the skills ... and skill-local `uv run` scripts that call the same validators"; "That last principle argues against making a BMAD manifest the only place the standard's rules are enforced, because an SWG cannot be expected to adopt a BMAD-specific pipeline."

Assessment:
- **Not hedging.** The premise that `bmod.toml` can run or enforce things is false, and I verified that: `setup.py` has no subprocess call, nothing reads a `setup` table, and unknown tables pass the validator (my trial `review-trial/b`: the proposal's `[bmod.setup.metanorma]`, `[bmod.dependencies]`, `[bmod.install_messages]` and `[[bmod.questions]]` all pass and do nothing). R2 changed the user's paradigm because the paradigm is not implementable, and says so.
- **Duplicated gate.** The layer table says the authoritative gate is `tools/gate/` in the standard repository and the agent-side copy is "the same gate scripts exposed as `uv run` scripts in skills". The skeleton shows both `ogcspec-gate/scripts/gate.py` in the module and `tools/gate/` in the standard repository. R2 never says which is canonical or how they stay identical. Two copies of the rule engine will drift, and the module's copy is the one an agent can skip.
- **Weak reason.** 26-021 is a discussion paper, "not a specification" (N-GOV), and its sentence is about OGC policies, not an SWG's repository CI. The solid reason is r29's collaboration-environment rule (see F3), plus OGC's own Metanorma CI conventions. R2 uses the weak reason in the summary and the strong one only implicitly.
- **Missed design A (in-paradigm).** The module declares the gate as `[skill] scripts = ["scripts/gate.py"]`, which setup installs to `_bmad/ogcspec/scripts/`, and CI and `.bmad-loop/policy.toml [verify] commands` both call that one copy via `uv run`. That uses `bmod.toml` to manage distribution and versioning of the pipeline, which is arguably what the user meant, with no second implementation. Cost: the standard repository's CI then depends on a BMAD-managed path, which conflicts with the OGC-controlled-repository rule. A vendored copy released from the module repository resolves that, but it is a design choice R2 should have laid out.
- **Missed design B (OGC-native).** ModSpec Part 3 is an XML and Schematron part, and OGC uses Schematron elsewhere. The rules in F1 are natural Schematron or XSLT assertions over Metanorma's semantic XML, which is language-neutral, runs without BMAD or Python, and matches the "no toolchain specified" principle R2 cites. R2 does not mention it.
- **Missing cost-benefit of packaging at all.** The module's real functions are free-text config questions, install messages, update checks and help. For a single repository with one team, repo-local Agent Skills carry the same `SKILL.md` content. R2 offers repo-local skills only as the v6 path. It never compares module versus repo-local on v7.

Fix: state one canonical gate implementation and where it is vendored; give the real reason (r29 collaboration rule) first; add Schematron-over-semantic-XML as an option in the spike list; add a one-paragraph module-versus-repo-local decision.

### F3 (High). Governance: one sentence conflates repository with tooling; licence, copyright statement, migration and verbal-form policy are missing

Location: R2 governance section, last sentence of paragraph 1; "Identifier provenance" paragraph; carried-over open items.

Claims quoted: "Once an SWG exists, any agent tooling that writes the working text should run inside the OGC-controlled collaboration environment, which a private BMAD pipeline in the submitter's own repository is not." Intro: "OGC's IPR text requires an accountable 'Contributor'". "Under r29 §8.4 ... before the first public release."

Problems:
1. **Rule scope.** r29 says "Non-OGC private repositories or projects may not be used for development of SWG deliverables" (verified verbatim in `dl/r29.txt` line 462, under "SWG use of collaboration environments"). That constrains where the *text* is developed. It does not forbid a contributor running local agent tooling against a clone of the OGC repository, and R2's own architecture keeps the module in a separate repository. The sentence as written implies the tooling must move. The accurate implication is different: at SWG formation the standard repository, including `tools/gate`, must move into (or be mirrored to) the OGC-controlled GitHub or GitLab organisation and carry the mandated README statement ("contributions ... belong to OGC"), and the repository history will contain agent-assisted commits. R2 recommends no migration plan.
2. **Licence and ownership of this repository.** `/home/nh/autonomyml/LICENSE` is the MIT licence of "Start Bootstrap LLC" (a website template; the repo is a GitHub Pages site). OGC IPR §4.1 vests copyright in the standard in OGC. Putting normative text into this repository under MIT, with a single committer and agent co-authorship trailers, creates a rights-chain question R2 never raises. Cheapest fix: keep normative text out of this repository until a contribution agreement and licence are chosen, or put it in a new repository with an explicit contributor statement.
3. **Redistribution of OGC text.** R2's skeleton ships `references/modspec-r7-rules.md` in a public module. OGC document licences permit copying only with copyright notices intact (the licence block is visible at the top of `20-059r4.html.txt`, which is the same pattern). R2 does not mention this. Cite and link, or carry the notice.
4. **The Naming Authority reviews the repository.** r29 §8.4 (`dl/r29.txt` line 930): "The candidate Standard document/repository will also be provided to the OGC-NA to ensure that document tags and formatting are consistent with the OGC Standard template and suitable for ingestion into the OGC Knowledge Management database." This is the strongest textual hook for the YAML-versus-AsciiDoc decision and R2 misses it (R2 only says "ask whether editors accept generated blocks"). See F4.
5. **Timing imprecision.** R2 says NA review happens "before the first public release". r29 line 922 says interim public comment periods "do not require OAB or OGC Naming Authority review"; the review precedes the official 30-day comment period.
6. **Overstated intro.** The intro says IPR "requires an accountable Contributor". The IPR defines Contribution and Contributor (a Member, a Representative, or "any other person or entity making a Contribution") and attaches licensing duties; it does not say who must author text. The body correctly labels the "tool is not a Contributor, so a human must make each contribution" step as R2's own reasoning, but the intro reads as policy. Also, the r29 text R2 cites for the editor ("not necessarily the author") cuts the other way: OGC does not require human authorship, only editorial responsibility.
7. **Draft ModSpec Policy 25-001 unread and unused.** The `ogc-modspec` clone contains `sources/ogc-modspec-policy` (docnumber 25-001, status Draft, received 2026-03-07). It resolves two items R2 and R1/R0 list as open: "the separate policy document that took over content moved out of ModSpec 1.1 is unidentified" (R2 line 230; R0 line 94) and, via the sibling release notes `sources/release-notes-1-1` (docnumber 25-003r3, which also fixes the 25-002 versus 25-003 discrepancy in favour of R2), the r3 to r7 change list. As a draft (not approved; `:status: Draft`) it would mandate: new OGC Standards comply with ModSpec Core "and relevant Parts"; the Abstract Test Suite is Annex A and normative; each component has a unique URI conformant to the Naming Authority; verbal forms follow **ISO/IEC Directives Part 2 Clause 7**; exceptions need a TC vote; Community Standards may opt out. Consequence: if 25-001 is approved as drafted, the "RFC 2119 keyword" review lens that R0 recommends is mis-specified for OGC (the policy names ISO verbal forms: shall, should, may, can; r7 itself writes them in uppercase italics). Neither R2 nor R1 mentions this, and the draft's status needs checking with OGC.
8. **OGC membership is assumed, not examined.** R2's accountability chain (a named human Member Representative makes each contribution, commits the patent licence, signs off) presumes the committer belongs to an OGC member organisation. R1 records that an SWG needs three members including a TC voting member and that fees are not public; R2 does not ask whether the owner or their organisation is a member, which gates whether any of the "human gate" controls can be exercised at all, and whether the pre-SWG phase is an external Submission of Technology. Cheapest closure: ask the owner, then OGC staff.
9. **Which ModSpec does the OAB apply?** r29 (line 926) names "Modular Specification Policy ... (08-131r3)" as the OAB criterion, and CS API (2025) cites r3. R2 tells agents to ground on r7 and calls r3 "outdated". That is probably right for a 2027 submission, but the formal reviewer text still says r3 and the r3 to r7 delta is only now readable. State the uncertainty and ask OGC. Note also that r3 already says recommendations are not tested (`r3.txt` lines 771, 1057), so M4's contradiction is independent of staleness; the intro's "stale ... or contradicted by the current standard" framing suggests otherwise.

Fix: reword the sentence as above; add a "repository lifecycle" paragraph (pre-SWG private, SWG-formation migration, README statement, licence, SoT form); read 25-001 and 25-003r3; treat the RFC 2119 lens as provisional and base it on ISO/IEC Directives Part 2 Clause 7 unless OGC says otherwise.

### F4 (Medium-High). "Structured YAML records" is adopted de facto while described as open, and the supporting inference is a non sequitur

Location: R2 "Reconciling the new goal ...", paragraph 2; Conclusion ("structured-records-and-CI core is kept and sharpened"); skeleton (`records/*.yaml`, `schema/*.json` beside `requirements/`, `abstract_tests/`).

Claims quoted: "One decision remains open and I do not settle it: whether the YAML or the AsciiDoc is the source of truth." Also "That favours schema-constrained structured records over free AsciiDoc generation by an agent".

Problems:
- The skeleton and layer table already assume YAML records plus a generator. The Conclusion calls the question "the one genuinely unresolved design question" while the intro says the earlier recommendation is reconciled "without overriding it". It is adopted, with a spike as a safeguard. That is acceptable but should be stated as a default, not as an open question.
- The quality evidence does not discriminate between YAML and AsciiDoc. ModSpec blocks written with `[%metadata]` and definition lists are themselves structured and are checked from semantic XML in R2's own gate. The studies support deterministic checks on agent output, not a particular storage format. Adding a YAML-to-Liquid-to-AsciiDoc stage introduces a second representation, error messages that point at generated lines, and the very drift problem F2 describes. The Liquid route is unexecuted and the Metanorma blog template contains non-standard Liquid (R2 admits this).
- R0's "cheapest way to keep the OGC option open" argument rested on OGC being undecided. With OGC decided, the relevant constraints are OGC's: template-consistent repository (F3.4), one-file-per-requirement practice, and editor acceptance. R2 should have re-derived the default from those, not carried it forward.

Fix: present the choice as a decision with criteria (NA repository review, editor acceptance, error localisation, diff readability), recommend a time-boxed spike on a 6-block fixture, and name the fallback.

### F5 (Medium). Quality-study figures are misdescribed; the inference is directionally fine but weaker than stated

Location: R2 governance section, quality paragraph.

Claim quoted: "In a 2026 study of 30 LLMs writing TLA+ specifications, models reached up to 26.6% syntactic correctness but only 8.6% semantic correctness against the SANY parser and TLC model checker".

Checked at https://arxiv.org/html/2606.05792v1 (fetched today): the 26.6% is a pooled pass rate (173 of 650 runs passing SANY under few-shot prompting) and 8.6% is 56 of 650 runs passing TLC under *progressive* prompting, a different prompting strategy. Individual models score far higher: GPT-5 passed SANY on all 26 specifications (100%) and TLC on 7 of 26 (26.9%); one open model reached 92.3% SANY. So "models reached up to 26.6%" understates frontier syntactic ability and compares unlike conditions. The correct reading is that syntactic validity is easy and semantic correctness is not, which supports R2's point more strongly than the quoted numbers do. R2's notes (N-GOV §3) record GPT-5's 100% SANY result, which the report body omits. Caveat on my own check: the 173/650 and 56/650 breakdown came from a fetch-tool summary of Table 3, not a direct read of the table; the abstract's "up to 26.6% ... only 8.6%" wording is what R2 paraphrased, and the abstract itself does not define the denominators.

Second study (https://arxiv.org/html/2504.01294v1): checked. 603 specifications, 37 documents (ArduPilot, PX4, Autoware), Claude 51.7% end-to-end and 71.6% annotation-then-conversion, the sentence-ID rejection is as described. It is *extraction from existing documents*. R2 draws a link to "invented `/req/...` names" by analogy; but new identifiers are by definition not yet in the repository, so "reject IDs that do not exist" catches dangling references only, not wrong-but-existing references or fabricated semantics. R2 does call the transfer an inference; the "closest analogue" language still overreaches.

Fix: restate the TLA+ finding with the pooled-versus-per-model distinction; downgrade the identifier analogy.

### F7 (Medium). The bmod.toml sketch passes the validator but contains internal inconsistencies and untested parts

Verified: R2's sketch, written exactly as given into `review-trial/a/` with placeholder skills, passes `validate_manifests.py` ("bmod files valid: 3 skills, 1 module records, 1 knowledge documents"; exit 0). I also confirmed the validator does *not* check that declared script files exist (the sketch declares `scripts/modspec.py`, which I never created) or the skill-name prefix, rejects `scripts/../x.py`, rejects `>=6.13.0` as a version, and rejects a missing `pre_install_message` (trials `c`, `d`, `e`). `init_skill.py --check` on a member skill fails with `name-format` unless `--any-name` is passed (documented flag); with it, all four skills pass. R2's "passes" claim is true but narrow, and R2 says so.

Inconsistencies in the sketch:

### F9 (Low-Medium). Small factual or logic defects

- R2 M14 regex `^/(req|conf|rec|per)/[a-z0-9-]+(/[a-z0-9-]+)?$` is flagged as "my inference", but it is narrower than the Naming Authority rule: 10-103r1 allows `name *("/" name)` (multi-segment) with `segment-nz-nc` characters (letters of either case, digits, `-`, `.`, `_`, `~`, and more), and its `class` production lists only `req` and `conf`, while r7 uses `rec` and `per` too. A gate built on this regex would reject legal names, and R2 does not note the 10-103r1 versus r7 mismatch.
- **`http` versus `https` is partly settled by the Naming Authority text R2 cites.** R2 says neither source "settles which a new standard should use". 10-103r1 §6.1 (in `dl/10-103r1.html.txt`) defines the generic syntax as `URI = "http://www.opengis.net/" OGCResource "/" ResourceSpecificPath`, and the Policy Directives say new identifiers "shall be http URIs, instead of URNs" (N-GOV §5). r7 (2026) uses `https://www.opengis.net/spec/modspec-1/1.1/`. So the policy text says http, the newest standard shows https; the policy documents date from 2021. Still unresolved, but the spike should ask the Naming Authority, and the gate should not hard-code either scheme.
- R2 omits ModSpec's "requirements package" concept (renamed from "module" in 1.1; release notes change 5) from the invariants and from the skeleton.
- R2 presents Req 20 as "a Core class exists" while R1 and R2 both carry CS API's missing Core class as uninvestigated; the gate would fail the closest precedent.
- "Policy 05-020r29 adds ... Standard Editor answers for 'the editorial quality of the document'": accurate quote; used to support accountability although the same sentence says the editor "is not necessarily the author" (see F3.6).
- R2 notes `-S/--strict` is declared in the CLI but unconsumed. I re-grepped metanorma, metanorma-cli, standoc, ogc, isodoc, utils, core: only the Thor option, `thor_with_config.rb`, and the copy in `compile_options.rb` line 207 into output options.
