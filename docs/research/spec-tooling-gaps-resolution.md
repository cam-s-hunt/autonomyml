# Evidence demotes OpenSpec and promotes structured requirement records

The evidence resolves most of the tooling gaps in the adversarial review, and it mostly confirms the review's skepticism. **Finding 1 is confirmed**: OpenSpec v1.16.0 has no per-requirement ID, class, dependency or conformance-target metadata. A requirement's identity is its header text, and stable IDs sit in an unmerged pull request. **Finding 2's pivot is sharper than the review stated**: the full OGC track requires ModSpec-style requirements classes plus an Abstract Test Suite, and its templates are Metanorma AsciiDoc, so the real question is where requirement IDs live, not which authoring tool comes first. BMAD's traceability exists, but it is software requirements-to-test traceability and does not transfer to a standard. The W3C QA guidance is a stable but unmaintained 2005 Recommendation. Conformance-suite precedents (CEL, SCXML, Serverless Workflow CTK) offer reusable patterns but none for time-dependent semantics. **The revised recommendation: keep the PDF's three-contract split and conformance-corpus idea, but replace "OpenSpec backbone with Markdown requirements" with git-native structured requirement records using ModSpec-style URI IDs, CI checks, and Metanorma generation. OpenSpec becomes an optional, replaceable proposal workflow, and BMAD is used only for core review and elicitation skills.** Whether OGC submission is a goal is still a decision only the project owner can make. Structured records are the default because they cost little now and keep the OGC option open; if the owner rules OGC out, header-ID Markdown with rename rules and an external ID check is an acceptable fallback. Findings 3 and 4 concern the repo itself, and this research did not touch them.

## Finding 1: OpenSpec has no home for IDs, and its merge is under question

Requirement identity in OpenSpec is the header name. The archive merge keys a map on the normalized text after `### Requirement:`, and nothing parses an ID, class, dependency or target out of a requirement block ([specs-apply.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/specs-apply.ts), [parser](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/parsers/requirement-blocks.ts)). A RENAMED FROM/TO pair rewrites only the header line, so any external reference to the old header silently dangles. The only metadata extension point is a top-level `x-` key in a change's `.openspec.yaml`, which is per change, not per requirement ([docs/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md)). The maintainers' own contributors say the same: "Requirements have no stable identity beyond their heading text" ([#1967](https://github.com/Fission-AI/OpenSpec/issues/1967)).

Stable IDs are on the roadmap but not shipped. Issue [#2167](https://github.com/Fission-AI/OpenSpec/issues/2167) and the implementing [PR #1979](https://github.com/Fission-AI/OpenSpec/pull/1979), authored by a listed maintainer, propose visible bracketed IDs such as `### Requirement: [AUTH-3] Users sign in`. They were open and unmerged on 2026-11-06 with no release target, and the 1.16.0 changelog does not mention them. Even if merged, the CLI would only read IDs. It would not assign them, add classes, dependencies or targets, or produce coverage reports; the issue lists coverage and two-way traceability as out of scope. A community schema, `spec-driven-ids`, fills part of the gap with an external ID allocator ([#2157](https://github.com/Fission-AI/OpenSpec/issues/2157)), but it is not maintained by the OpenSpec project.

The review's finding about custom schemas is correct and can be sharpened. A schema controls which artifacts exist, their `requires` ordering, instructions, templates and the apply phase. It cannot change merge, validation or spec structure, because the schema types have no fields for them ([types.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/artifact-graph/types.ts), [customization.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/customization.md)). Dependencies are existence checks only. One community schema author states this directly: "OpenSpec only checks that artifacts exist, so enforce the gate with your own CI or hook" (same customization doc). A "proposal, normative delta, abstract tests, tasks" schema is expressible and `openspec schema validate` would accept it. But the abstract tests would be free-form files that archive moves to `changes/archive/` rather than promoting into a durable baseline, and nothing would check that each requirement has a test. Validate and archive discover only files named `spec.md` (there is no `openspec sync` CLI command; sync is an agent skill), so a YAML or JSON normative model would sit entirely outside what OpenSpec merges or validates. One contributor issue records the hard-coding ([#666](https://github.com/Fission-AI/OpenSpec/issues/666), open since February with no maintainer response).

The most consequential new fact is churn risk. The lead maintainer opened [#2033](https://github.com/Fission-AI/OpenSpec/issues/2033) on 2026-10-02 asking whether `openspec archive` should stop merging specs deterministically. He cites 46 fix commits to merge code since June 2026, and describes it as "an open question, not a proposal ready to implement". Open PRs [#2168](https://github.com/Fission-AI/OpenSpec/pull/2168) and [#2174](https://github.com/Fission-AI/OpenSpec/pull/2174) are reworking how the `specs` artifact is located. A standard whose baseline depends on exact archive behavior would be building on a mechanism its maintainers are reconsidering. The schema commands are also labelled experimental in the newer docs source ([docs-lab](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/customize/schemas.md)). A later trial of v1.16.0 found that `validate` ignores all non-Markdown files and Markdown without delta headers, rejects a non-`spec.md` Markdown file in a change's `specs/` that contains delta headers, and that `archive` is more lenient than `validate`.

## Finding 2: OGC submission makes ModSpec-shaped IDs the real decision

The path to a full OGC Implementation Standard is a draft SWG charter, a Standards Working Group (formed when three or more members, including at least one voting member, submit a candidate standard), a 30-day public comment on the candidate, a 45-day TC electronic vote, then Executive Planning Committee approval ([OGC 05-020r29](https://docs.ogc.org/pol/05-020r29/05-020r29.html)). Each new SWG must commit to RAND Royalty Free standards. A candidate standard needs OAB approval before public release. Three or more documented implementations are required for Full Standards at Draft stage. For Full Standards the policy requires "clearly defined Requirements" plus an Abstract Test Suite, and the Naming Authority checks consistency with the OGC Standard template. The one dated anchor is OGC API - Connected Systems Part 1 (23-001): submitted 2025-03-19, approved 2025-06-02, published 2025-07-16 ([OGC 23-001](https://docs.ogc.org/is/23-001/23-001.html)). 05-020r29, titled 'Technical Committee Policies and Procedures', is the newest public revision and is still linked from OGC's policy index (checked 2026-11-06; a members-only successor cannot be ruled out). The charter public review is three weeks (4.6.2); the 30-day period applies to the candidate Standard (8.4.4).

The Community Standard route is lighter but a poor fit for a new language. The policy lists the OGC template and Modular Specification as "Not required" for it. But it needs three endorsing member organizations, evidence of implementation in multiple products or widespread use, and the content is "normatively-frozen once [it enters] the approval process" ([05-020r29 §8.4](https://docs.ogc.org/pol/05-020r29/05-020r29.html)). AutonomyML has a Go reference runtime but no multi-implementation record yet, so this route is premature.

On Metanorma, no sentence in the policy text the researchers could read names it as mandatory, but the templates the policy points to "are built to work in the Metanorma publishing environment" ([opengeospatial/templates](https://github.com/opengeospatial/templates)). For a Full Standard Metanorma AsciiDoc is therefore effectively required. That is an inference from the templates repository, not a policy sentence. Real OGC practice, in the CS API source, is one hand-written AsciiDoc file per requirement (`[requirement,model=ogc]` with `identifier:: /req/system/canonical-url`), one file per requirements class with `subject::` and `inherit::`, and abstract tests in a normative Annex A with `/conf/...` identifiers ([CS API repo](https://github.com/opengeospatial/ogcapi-connected-systems)). The PDF's claim that Metanorma supports YAML as the authoritative source is correct: a 2024 Metanorma post keeps requirements, conformance classes and tests in YAML and renders them through Liquid templates into those blocks ([Metanorma blog](https://www.metanorma.org/blog/2024-04-04-ogc-modspec-in-yaml/)). Caveats: the successor mechanism, data2text, was not read, the pattern's compatibility with ModSpec 1.1 terminology is unverified, and the researchers found no OGC standard that uses it in production. Nor does the blog's design generate or validate IDs. Migrating free-form Markdown to Metanorma has no documented tooling. The expensive steps are designing URI-style IDs, grouping requirements into classes, and writing a test per requirement, which are design decisions rather than syntax conversion. That supports the review's warning that late migration is the costly path.

## Findings 3, 4 and 5: repo-internal findings stand, and primary sources now exist

Findings 3 (duplicated example JSON) and 4 (no normative language yet, pilot already drafted at runtime-doc §4.4) concern the AutonomyML repository itself, and the notes did not re-examine them. They stand as written, and the CS API layout supports the fix for finding 3: schemas and `examples/` live as separate machine artifacts from the normative document. Finding 5 (padded references, third-party sourcing) is partly answered by this research. Primary sources for OpenSpec, BMAD, ModSpec and Metanorma are now in hand, so the PDF's blog-sourced claims can be replaced. The 192-reference list itself was not re-audited, and the "autonomy.mil" retrieval-drift hypothesis stays unconfirmed.

## Finding 6: the "checked" items hold and the weak items resolve

The ModSpec claim is confirmed: Part 1 Core v1.1 (08-131r7) was submitted 2025-10-20, approved 2026-03-05 and published 2026-05-21 ([OGC 08-131r7](https://docs.ogc.org/pol/08-131r7/08-131r7.html)). The review's "unmentioned Parts 2 and 3" is resolved as not relevant: Part 2 (24-065r1) is an optional UML extension and Part 3 (24-066r1) an optional XML/Schematron extension ([24-065r1](https://docs.ogc.org/pol/24-065r1/24-065r1.html), [24-066r1](https://docs.ogc.org/pol/24-066r1/24-066r1.html)). There is no JSON Schema part. Part 1 plans one as "Part 5", and says standards using an uncovered mechanism are "tested only on the structure of their conformance test suite" until it exists. That gap does not block AutonomyML. CS API Part 1 already pairs ModSpec structure with JSON Schema 2020-12 and an Annex A ATS.

For BMAD's "requirements-traceability support", the claim is real but labelled loosely. It refers to the optional TEA module (pinned at its last v6 release, v1.27.2), whose `trace` workflow produces a `traceability-matrix.md` and a deterministic PASS/CONCERNS/FAIL/WAIVED gate (PASS needs P0 at 100%, P1 at least 90%, overall at least 80%) ([run-trace.md](https://raw.githubusercontent.com/bmad-code-org/bmad-method-test-architecture-enterprise/v1.27.2/docs/how-to/workflows/run-trace.md)). Its oracle is stories, a PRD, OpenAPI or code, and its tests are executable repo tests. Nothing in BMAD maps normative requirement IDs to conformance tests or abstract test suites. Core BMM adds stable FR and CAP IDs and forward/backward coverage checks, but its PRD skill says to "skip traceability matrices" ([bmad-prd SKILL.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/src/bmm-skills/plan/bmad-prd/SKILL.md)). The researchers read the TEA how-to document, not the `trace` skill source. Using it for a standard is plausible only if the conformance corpus runs in-repo, and it is undocumented.

The previously unchecked claim that BMAD carries planning artifacts into an existing delivery workflow is verified, almost word for word, as the README tagline ([README line 14](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/README.md)), which I re-confirmed in the local clone. The mechanisms are prompt-level hooks (`external_handoffs`, `on_complete`) that push to Jira, Confluence, Notion or Linear, and a `stories.yaml` dispatch file ([adopt-bmad-across-a-team.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/customize/adopt-bmad-across-a-team.md)). They do not connect to a spec-delta tool: v6.12.4 contains zero references to OpenSpec or Spec Kit. The PDF's phrasing is therefore accurate but means something different from what the OpenSpec pairing needs.

The review's other two "checked and correct" items also hold. OpenSpec supports project-local custom schemas and its archive merges only specific delta structures (see finding 1), and BMAD supports custom modules, installed from a Git URL or local path and scaffolded with the BMad Builder module (`bmb`; v6.12 route, on v7 the Toolsmith skill replaces BMad Builder) ([add-modules.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/customize/add-modules.md)).

Two BMAD items were unverified in the first pass and are now resolved. The BMAD research brief asked about `bmad-toolsmith` and `bmod.toml`. A follow-up check found they exist on BMAD main (v7 preview alpha) since 2026-09-20 (`bmod` records) and 2026-10-06 (Toolsmith), and are absent from v6.12.4 and every release and npm version. v6.12.4 (2026-10-14) was the latest GitHub release and npm `latest` on 2026-11-06. The v7 contents beyond these items were not examined.

## Finding 7: the comparison table has no independent evidence in either direction

No independent evidence exists on OpenSpec, BMAD or Spec Kit for standards or other non-software specification work. Comparison pages the researchers saw were software-coding blogs they did not fetch ([example](https://dev.to/willtorber/spec-kit-vs-bmad-vs-openspec-choosing-an-sdd-framework-in-2026-d3j)), and no usage report of BMAD for a standard was found either. The table therefore remains opinion, but documentary evidence now supports its direction. For "BMAD alone: not first choice", the strongest support is structural. `bmad-spec` derives `SPEC.md` from an append-only memlog and calls a hand-edit "unsupported" and overwritten on the next derive ([bmad-spec SKILL.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/src/bmm-skills/plan/bmad-spec/SKILL.md)), which conflicts with humans authoring normative text in a repo. Its input ceiling is roughly 40 pages ([choose-a-planning-path.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/plan/choose-a-planning-path.md)), and it has no concept of normative versus informative text, conformance targets or requirements classes. The counterweight is that `bmad-spec` is explicitly domain-generic ("software, game design, research, editorial, policy, business") and `spec_template`, review lenses and custom modules are all overridable. The inference that these overrides can build a standards module is feasible by design but untested; no such lens or module exists.

For "OpenSpec alone: strongest lightweight starting point", the evidence is mixed. It is lightweight, but it is a software change-management tool whose own contributors describe its specs as filling with implementation detail ([#1967](https://github.com/Fission-AI/OpenSpec/issues/1967)). For "Full BMAD + OpenSpec everywhere risks duplication", the concern is consistent with BMAD's rule that every document has one owner skill, but it is design reasoning, not documented breakage. Directory and skill namespaces do not collide by default; the one shared surface is a managed block in `AGENTS.md`, and OpenSpec v1.16.0 `init`/`update` leave root `AGENTS.md` and `CLAUDE.md` untouched, other than stripping legacy `OPENSPEC` marker blocks (tested with synthetic BMAD markers, not BMAD's real `bmad:context` block). The BMAD review stack is the part that holds up best for "selective BMAD". The `bmad-review` lenses (adversarial, edge-case-hunter, structure, prose), advanced elicitation (red team, pre-mortem, steelman) and party mode are domain-generic, and lenses can be added through `customize.toml` ([bmad-review customize.toml](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/src/core-skills/bmad-review/customize.toml)). One caution: the adversarial lens demands at least ten findings, while the skill's own intro says empty results are valid, so a review of a clean draft would need triage for padding. Skill names also changed heavily across v6.11 and v6.12 (for example `bmad-quick-dev` became `bmad-build`) and v7 is in preview alpha, unreleased, ETA mid-November 2026 ([CHANGELOG](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/CHANGELOG.md)), so overrides keyed to skill names face another migration.

## Finding 8: the W3C QA guidance is stable, dated and useful for vocabulary

"QA Framework: Specification Guidelines" is a W3C Recommendation dated 17 August 2005, with 13 requirements and 23 good practices, covering conformance clauses, scope, terminology and managing variability ([QA Spec Guidelines](https://www.w3.org/TR/qaframe-spec/)). Its status says it "is a stable document and may be used as reference material". The QA Working Group closed in August 2005 and the Interest Group in 2007 ([QA WG](https://www.w3.org/QA/WG), [QA IG](https://www.w3.org/QA/IG)). The researchers found no superseding document, but also no maintenance, and did not finish a supersession check against W3C Process or Manual of Style material. The PDF should call it a dated but stable checklist, not current W3C requirement. The companion Note "Variability in Specifications" (31 August 2005) is arguably more useful: it defines profiles, modules and extensions and says editors should document limits on combining them, which gives vocabulary for the repo's Layer 1/2/3 model ([spec-variability](https://www.w3.org/TR/spec-variability/)). The W3C TAG's Web Platform Design Principles Note offers contemporary spec-writing guidance, but the fetched copy's date (2 November 2026) is unverified, as are its conformance sections.

## Finding 9: Building Blocks fit the schema layer, conformance precedents guide the suite, and dependencies need a table

**Building Blocks.** OGC Building Blocks are a GitHub template plus postprocessor for JSON-Schema-centred components, with examples, JSON-LD contexts, SHACL shapes and a generated register ([bblocks-postprocess](https://github.com/opengeospatial/bblocks-postprocess), [bblock-template](https://opengeospatial.github.io/bblock-template)). Validation runs JSON Schema, then JSON-LD uplift, then SHACL, and test files ending `-fail` pass only if validation fails ([validation docs](https://ogcincubator.github.io/bblocks-docs/create/validation)). That matches `examples/` plus the `semvocab` layer well, adds negative fixtures the repo lacks, and needs no OGC membership. But Building Blocks carry no requirement-class or conformance-class semantics, so they complement ModSpec rather than replace it. The researchers found no Building Blocks plus Metanorma hybrid in CS API (its tree has zero `bblock` paths), and did not check whether SensorML 3.0, SWE Common 3.0 or CS API are registered as blocks, so the hybrid is a design proposal, not a precedent.

**Conformance suites.** The Serverless Workflow CTK is Gherkin features (arrange a workflow definition and input, act "the workflow is executed", assert complete/fault/cancel, output, and task ordering), but it has no event model, timing handling or documented version pinning ([CTK README](https://github.com/open-workflow-specification/specification/blob/main/ctk/README.md)). Only `try.feature` was read, so its timing coverage is unverified. Better models for time-dependent semantics are elsewhere. CEL's conformance cases carry a `result_matcher` oneof that includes `any_eval_errors` and `any_unknowns`, expressing a set of allowed outcomes, and its files are grouped so implementations can skip a subset ([simple.proto](https://raw.githubusercontent.com/google/cel-spec/master/proto/cel/expr/conformance/test/simple.proto)). SCXML's Implementation Report Plan has about 196 assertions, each tagged mandatory or optional in a manifest. Each test is a state machine that reaches a pass or fail state, and `conf:delay` lets implementations shorten delays ([SCXML IRP](https://www.w3.org/Voice/2013/scxml-irp/)). BehaviorTree.CPP's tests use real clocks with CI-jitter margins and are not a portable suite ([gtest_wakeup.cpp](https://raw.githubusercontent.com/BehaviorTree/BehaviorTree.CPP/master/tests/gtest_wakeup.cpp)). No precedent found uses golden traces for time-dependent execution. The practical design is therefore scenario, controlled clock, scripted events and a set of allowed terminal states or partial orders. Requiring conformance runners to support a virtual clock is a design inference, not a precedent. The DMN TCK and BPMN MIWG file formats were not read, and no OGC executable test suite for CS API was found. The repo says `semconnect` is "verified against OGC conformance suites", and which suites exist is unverified.

**Normative dependencies.** OGC versions standards on a major.minor pattern in which a minor revision is backward compatible (Directive 18), and treats referenced schemas as normative by namespace and location (Directive 24) ([OGC Policy Directives](https://portal.ogc.org/public_ogc/directives/directives.php)). CEL has no formal language version, and cel-spec references appear only incidentally, such as v0.7.0 ([langdef.md](https://github.com/cel-expr/cel-spec/blob/master/doc/langdef.md)), so the conformance-file set plus a repo tag or commit is the de facto pin. CS API Part 1 normatively cites SensorML 3.0 (23-000), OGC API - Common Part 1, GeoJSON RFC 7946 and JSON Schema 2020-12 but not SWE Common, which appears only in design considerations ([OGC 23-001](https://docs.ogc.org/is/23-001/23-001.html), first ~100k of ~444k characters read). The approval status of SensorML 3.0, SWE Common 3.0 and CS API Part 2 on docs.ogc.org was not confirmed; the GitHub v1.0.0 bundle is marked Pre-release ([release](https://github.com/opengeospatial/ogcapi-connected-systems/releases/tag/v1.0.0)). A normative-references table giving exact identifier and version, dependent clauses and an upstream-update rule is a derived recommendation, not a documented OGC practice. The SHACL precedents add one caution: DCAT-AP ships its shapes as part of the specification ([SEMICeu/dcat-ap_shacl](https://github.com/semiceu/dcat-ap_shacl)), but validation behavior varied by engine, so conformance wording should name a reference validator or restrict itself to SHACL Core. Also unresolved is how the Layer 1/2/3 model maps onto ModSpec requirements classes and profiles; the notes call this mapping an inference that was not verified against the repo.

## Revised recommendation: structured records first, OpenSpec optional

The PDF's direction survives and its starting arrangement changes. Keep the thin orchestration layer, standards-first thinking, the three-contract split and the conformance-corpus idea. Change five things.

First, make the normative source structured records (YAML with ModSpec-style fields: `identifier` of the form `/req/<class>/<name>`, statement, class, target type, dependencies, and a paired `/conf/...` test), not OpenSpec-compatible Markdown. It is the cheapest way to keep the OGC option open, since Metanorma's documented yaml2text/data2text pattern or a small generator can emit `[requirement,model=ogc]` blocks later, and it avoids a header-embedded ID that breaks on rename. If the project owner answers "OGC submission is not a goal", Markdown with an ID in the header is acceptable, but only with explicit rename rules and an external ID check, because OpenSpec supports nothing here. If the answer is "yes or likely", add Metanorma generation immediately and design requirements classes around the Layer 1/2/3 model. Do not pick the Community Standard route before multiple implementations exist.

Second, demote OpenSpec from backbone to optional proposal workflow. It can still manage proposal, design and tasks around changes, but it cannot merge, validate or carry the structured baseline, its archive merge is under maintainer review (#2033), and its stable-ID feature is unmerged. If used, pin the version, keep the normative baseline outside `openspec/specs/`, and treat it as replaceable. Plain git, pull requests and CI scripts may be sufficient on their own; the evidence shows OpenSpec adds workflow convenience, not standards capability.

Third, put the enforcement in CI instead of in tooling that cannot provide it: ID uniqueness and format, every requirement has a conformance test, no normative text duplicated across files, and `examples/` validated against JSON Schema and SHACL with positive and `-fail` fixtures, using a Building Blocks style pipeline. Make `examples/` the single source for example JSON (finding 3).

Fourth, use BMAD selectively and narrowly: core-only install, with `bmad-review` lenses (add custom "normative-delta", "conformance" and "RFC 2119 keyword" lenses), advanced elicitation and party mode with implementer, certifier and tester personas. Skip `bmad-spec`, Build and sprint machinery, and do not rely on TEA `trace`. Budget for v7 migration and treat any BMAD output as input to the owned records, not as a second source of requirements.

Fifth, build the conformance corpus as scenario files with a machine-readable case format, a mandatory virtual-clock requirement, allowed-outcome sets, and per-profile manifest tags (CEL, SCXML and CTK patterns), separate from the OGC-style ATS annex that maps abstract tests to requirements. Cite the W3C QA Guidelines as a dated checklist and the Variability Note for profile vocabulary, and maintain a normative-references table with pinned versions, including CEL by tag and conformance-file set.

## Conclusion

The review's central insight, that the PDF's arrangement rested on an unasked question and an absent capability, is stronger with evidence: the decisive factor was never Markdown versus YAML but whether requirement identity and the requirement-to-test link are first-class data. OpenSpec lacks that today, BMAD's traceability is shaped for software, and OGC's pipeline demands exactly that structure, so structured records are the low-regret default, and header-ID Markdown is a defensible fallback only if OGC is ruled out. The finding most worth acting on is the maintainers' own reconsideration of OpenSpec's deterministic archive, because it makes any plan that depends on exact OpenSpec merge semantics a bet against its authors' current direction.

Two things the evidence cannot settle will shape the final decision. The first is the owner's answer on OGC submission, together with the costs of the OGC path: membership fees are not public (calculator only); a SWG needs three or more members including one TC voting member (30-day opt-in wait for individual voting members); the public-comment close to approval took roughly seven months in two Full-track examples and about ten in one Community example. The second is whether the novel conformance format, a trace-with-tolerance suite, can be specified tightly enough to be language-neutral; no precedent covers it.

## Remaining open items

- OGC submission goal: undecided by the project owner; membership fee tiers are not public; TC voting rights (Technical/Principal/Strategic in r29; Catalyst and above on current pages, mapping inferred) are needed for the one required voting member.
- OGC policy currency: 05-020r29 confirmed current on the public record (2026-11-06; a members-only successor cannot be ruled out); charter review three weeks versus candidate comment 30 days reconciled; the 6-9 and 18-24 month figures are dropped as unsupported. Examples: roughly 7 months (Full, two cases) and 10 months (Community, one case) from public-comment close.
- Metanorma mandate: no policy sentence names it as mandatory, so "effectively required" is an inference; data2text syntax and ModSpec 1.1 compatibility of the yaml2text pattern are unverified; no production use of YAML-to-Metanorma in an adopted OGC standard was found.
- ModSpec: the separate policy document that holds the content moved out of 1.1 is unidentified; the release notes (25-002) are a draft with an internal numbering error; whether any group has started the JSON Schema part is unknown; the tension between ModSpec's required Core class and CS API's "no Core requirements class" is uninvestigated.
- OpenSpec: merge status and release timing of PR #1979, and the outcome of #2033, are unknown; `/opsx:sync` agent behaviour with extra files is untested; the `ml-research`, `anvil` and `epic-driven` schemas were not read.
