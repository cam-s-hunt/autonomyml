# Rebuild the OGC module around CI, not bmod.toml

**The proposal's goal is sound, but its manifest is almost entirely invented, and its central mechanism does not exist.** Of the `bmod.toml` keys it uses, only `[bmod]`, `code` and `version` are real; `source`, `members`, `description`, `[bmod.dependencies]`, `[[bmod.questions]]`, `[bmod.install_messages]` and `[bmod.setup.*]` are either wrong or ignored, and nothing in BMAD reads `strict_validation = true`, runs Metanorma, or fails a build on a manifest's say-so. The Metanorma and ModSpec content has the same pattern: the compile command, the flavors and the role-style blocks are real, but `label=`, the `/req/model/` prefix, `validate_schema`, and the linter rule "every requirement needs a recommendation or permission leading to an abstract test" are stale, nonexistent, or contradicted by the current standard (OGC 08-131r7). The corrected design has three parts: the authoritative validation pipeline lives in repository CI and stays BMAD-independent; a thin BMAD module packages the skills, personas and skill-local `uv run` scripts that call the same validators; and humans keep authorship, identifier minting and Naming Authority submission, because OGC's IPR text requires an accountable "Contributor" and its identifiers are controlled by the Naming Authority. This reconciles with the earlier recommendation (structured YAML requirement records, CI validation, OpenSpec optional, BMAD for review lenses) without overriding it, except at one point I flag rather than settle silently: the earlier advice to pin stable v6.12.4 conflicts with a module that can only exist on unreleased v7 `main`, a preview alpha whose release is targeted for mid-November 2026. All BMAD findings are against `main` commit `e734d3ac` (2026-11-06). The corrected `bmod.toml` below passes BMAD's own `validate_manifests.py` when run locally; none of the Metanorma behaviour was executed, only read from source and docs.

## Fifteen BMAD claims audited: three hold, the rest are invented or misplaced

The proposal's BMAD vocabulary is a plausible extrapolation, not a description of a shipped feature. `bmod.toml` exists on `main` but not at v6.12.4: the `bmod` records arrived on 2026-09-20 and Toolsmith on 2026-10-06, and the newest GitHub release on 2026-11-06 is still v6.12.4, published 2026-10-14 ([README on main](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/README.md), [releases](https://github.com/bmad-code-org/BMAD-METHOD/releases)). The runtime parser reads a fixed set of fields and, by design, "ignore[s] every other key and table" so that a newer file never blocks an install ([setup.py `parse_bmod_file`](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/skills/bmad/scripts/setup.py)). The practical consequence is that the proposal's file would validate after five fixes and then silently discard every OGC-specific table. I reproduced that locally: with the proposal's `[bmod.setup.metanorma]`, `[bmod.dependencies]` and `[bmod.install_messages]` tables present, `validate_manifests.py` reports the file valid once `update_source`, `skills` and both install messages are added ([validator](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/skills/bmad/scripts/validate_manifests.py)). Verdict key: SUPPORTED, PARTIAL, CONTRADICTED, NOT FOUND (no trace in any inspected BMAD repository).

## Fifteen Metanorma and ModSpec claims: the compile line holds, the requirement syntax and linter rule do not

The proposal's OGC half fails in more instructive ways, because the errors would produce documents that compile but mean the wrong thing. The ModSpec context it cites, OGC 08-131r3, is the 2009 "Specification Model"; the current document is 08-131r7, "The ModSpec Model - Part 1: Core", version 1.1, approved 2026-03-05 and published 2026-05-21, with a UML Part 2 (24-065r1) and an XML/Schematron Part 3 (24-066r1) ([OGC 08-131r7](https://docs.ogc.org/pol/08-131r7/08-131r7.html)). The outdated reference is understandable, since Metanorma's OGC authoring guide, the `modspec` Ruby gem and the CS API Part 1 conformance clause all still cite r3 ([Metanorma OGC authoring guide](https://www.metanorma.org/flavors/ogc/authoring-guide/), [CS API clause 2](https://github.com/opengeospatial/ogcapi-connected-systems/blob/master/api/part1/standard/sections/clause_2_conformance.adoc)), so toolchain vocabulary lags the standard and an agent primed from memory will encode the older model. The most consequential error is the linter rule. ModSpec r7 says "Recommendations and permissions are not tested although they should still be documented using a standard template and have unique labels and/or identifiers" ([08-131r7](https://docs.ogc.org/pol/08-131r7/08-131r7.html)), so a linter demanding that every requirement trace through a recommendation or permission to an abstract test would reject conformant documents. The real invariants are that every requirement is tested (Req 1), identifiers are unique (Req 2), requirements classes and conformance classes correspond one to one (Req 8), a conformance class tests one requirements class (Req 11), a Core class exists (Req 20), and each requirement sits in exactly one class (Req 28).

## Agents may draft records, but humans must sign, mint and submit

The governance record does not forbid agent assistance, but it pins accountability on people. OGC's IPR Policy defines a Contribution as "an affirmative and knowing contribution, in written or electronic form" and a Contributor as a Member, a Member's Representative, or "any other person or entity making a Contribution"; Contributors to a Standards Working Group (SWG) must commit to license patent claims at the time of contribution ([IPR Policy](https://docs.ogc.org/pol/Intellectual_Property_Rights_Policy_revised_15_December_2021.pdf) §§2, 3.2). Copyright in the resulting standard vests in OGC (§4.1). Policy 05-020r29 adds that submitters agree OGC owns the copyright, that "proprietary and confidential material is not included", that the Standard Editor answers for "the editorial quality of the document" while not "necessarily the author", and that "non-OGC private repositories or projects may not be used for development of SWG deliverables" ([05-020r29](https://docs.ogc.org/pol/05-020r29/05-020r29.html) §§4.13, 8.4, 8.8). **I found no OGC policy on AI-assisted authoring** on the public policy index checked 2026-11-06, though a members-only stance cannot be ruled out ([OGC policies](https://www.ogc.org/ogc/policies/)). Reading these together, a tool is not a "Contributor", so a human Member Representative has to make each contribution knowingly; the US Copyright Office adds that "prompts alone do not provide sufficient human control" for authorship ([USCO Part 2](https://www.copyright.gov/ai/Copyright-and-Artificial-Intelligence-Part-2-Copyrightability-Report.pdf)). That reasoning is mine, not OGC's, and it is not legal advice. Once an SWG exists, any agent tooling that writes the working text should run inside the OGC-controlled collaboration environment, which a private BMAD pipeline in the submitter's own repository is not.

Other standards bodies are stricter or still undecided. The W3C's March 2026 Group Note on LLMs in standards work says each individual is responsible for their own output and that LLM text "may contain subtle falsehoods, which are hard to spot", but it is a Note and does not decide whether LLMs may author normative text ([W3C Note](https://www.w3.org/TR/2026/NOTE-llms-standards-20260324/)). The IEC's version 1.1 guidance (October 2024) prohibits generative-AI text in IEC content unless the tool is supplied by the Secretariat, but a version 2.0 was reported on 2026-06-29 and I could not read it, so the v1.1 wording should not be taken as current; it matters only if the standard later seeks ISO/IEC adoption ([IEC v1.1 mirror](https://dev-web.electrosuisse.ch/wp-content/uploads/2025/01/Guidance_on_use_of_AI_for_IEC_Committees.pdf), [ANSI news](https://www.ansi.org/standards-news/all-news/6-29-26-iso-and-iec-publish-updated-guidance-on-the-use-of-ai-in-standards-development)). At the IETF, a proposal for an Internet-Draft disclosure question was made in February 2026 but no rule is adopted ([IETF list](https://mailarchive.ietf.org/arch/msg/ietf/PeEKEOL8QoUI9RI2aRYv4joQPmM/)).

Precedent for agents authoring normative text does not exist; precedent for agents reading and reviewing it does. Mark Nottingham's `ietf-skill` set offers contributing, reviewing, interpreting and HTTP skills, with `ietf-reviewing` producing "findings rather than a finished review" and a README disclaiming any official standing ([mnot/ietf-skill](https://github.com/mnot/ietf-skill)). Metanorma's own AI work is citation-grounded question answering over a corpus, with "mechanical post-generation verification", and its `metanorma-mko` MCP server is read-only ([metanorma/ai](https://github.com/metanorma/ai), [metanorma-mko](https://github.com/metanorma/metanorma-mko)). The recall and cost figures on the former page are the repository's own claims. OGC's discussion paper 26-021 frames AI as a consumer of standards, proposes that human-readable documents be derived from canonical machine-readable forms, and states that "policies should not specify software or toolchains" ([OGC 26-021](https://docs.ogc.org/techpaper/26-021.pdf)). That last principle argues against making a BMAD manifest the only place the standard's rules are enforced, because an SWG cannot be expected to adopt a BMAD-specific pipeline.

The quality evidence points at the same architecture. In a 2026 study of 30 LLMs writing TLA+ specifications, models reached up to 26.6% syntactic correctness but only 8.6% semantic correctness against the SANY parser and TLC model checker, and the authors conclude that LLMs "do not generate reliable TLA+ specifications without expert oversight" ([arXiv 2606.05792](https://arxiv.org/html/2606.05792v1)). A study extracting 603 expert-verified specifications from UAV documents found fabrication and oversimplification, with an end-to-end accuracy of 51.7% rising to 71.6% when annotation and conversion were separated, and it limited hallucinated references by rejecting sentence IDs that do not exist in the source ([arXiv 2504.01294](https://arxiv.org/html/2504.01294v1)). Both are preprints in adjacent domains with formal checkers that normative prose lacks. I found no study of LLMs writing ModSpec requirements, RFC 2119 keyword usage, or OGC conformance tests, so transfer is an inference. The inference is still actionable: identifier fabrication (invented `/req/...` names, clause numbers or references) is the closest analogue to the studied failure, and the matching mitigation is a deterministic check that every reference resolves to a record in the repository. That favours schema-constrained structured records over free AsciiDoc generation by an agent, and deterministic checkers over an LLM "ModSpec Linter".

Identifier provenance adds a hard boundary. OGC requires "an OGC name for each normative element", of the form `/spec/<standard>/<version>/req|conf/<class>/<name>`, where `<standard>` must be a registered doc-name and changes to the register "shall be initiated by a submission to the OGC Naming Authority" ([10-103r1](https://docs.ogc.org/pol/10-103r1.html) §§6.2, 7.1). Under r29 §8.4 the editor submits the candidate standard's namespace URI list for Naming Authority review concurrent with OAB review, before the first public release ([05-020r29](https://docs.ogc.org/pol/05-020r29/05-020r29.html)). My inference: agents must not assert a name is registered, mint a final standard doc-name or version token, or file Naming Authority requests; safe behaviour is drafting candidate names marked unregistered, checking syntax and in-repo uniqueness, and generating the review spreadsheet for the human editor. No OGC text sets a pre-registration placeholder convention, and no document explicitly permits or forbids script-submitted requests.

## A bmod.toml packages skills; the pipeline must live in CI

What a `bmod.toml` can do is bounded and well documented. It identifies a module, lists its member skills, pins minimum versions of other skills, asks free-text configuration questions whose answers land in `_bmad/config.toml` or the user-scoped file, ships text messages, names knowledge documents, and lists scripts that setup installs to `_bmad/<code>/scripts/` ([module-files.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/docs/reference/module-files.md), [add-modules.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/docs/customize/add-modules.md)). Beside it, the record folder can carry `roster.toml` (personas), `retired.toml`, migrations, `help/` and `doc-templates/`. The last is the one first-class extension point for new document types: any Markdown file with `template:` frontmatter there is offered by `bmad-facilitate`, with fields for a rubric, methods, `extends:` and per-section markers, and BMAD's Founder module ships nothing but templates and a rubric ([write-a-document-template.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/docs/customize/write-a-document-template.md)). What a `bmod.toml` cannot do is anything executable: `setup.py` contains no subprocess call or hook path, there is no key for external binaries, containers or environment variables, no way to register a validator or fail a build, no enumerated question types, and no variable substitution. The rubric is LLM-judged, and I found no parser enforcing a template's `required` markers.

The validation pipeline therefore has to be recomposed from three independent systems, and the only reliable gate is the one a pull request cannot bypass. A skill-local script is advisory because an agent may never run it; bmad-loop's `[verify] commands` and blocking `pre_commit_gate` hooks are real gates but belong to the consuming project's loop configuration and assume code stories, and whether the loop can drive a document-only ticket is unresolved (maintainer discussion #3147 asks exactly this and I saw no answer) ([discussion](https://github.com/bmad-code-org/BMAD-METHOD/discussions/3147)). The placement I recommend, which is a design synthesis rather than a documented BMAD recipe, is below.

| Layer | What it holds | Where it lives | Who enforces it |
|---|---|---|---|
| Normative records and generators | YAML requirement, class, test records; Liquid or script that emits `[requirement,model=ogc]` blocks | Standard's repository | Pull request review |
| Authoritative gate | Record schema; ModSpec r7 linkage (Req 1, 2, 8, 11, 20, 28); `/req` to `/conf` pairing; reference resolution; pinned-image `metanorma compile --agree-to-terms -t ogc`; log or XML severity check with recommendation/permission exempt | Standard's repository CI, BMAD-independent | CI status required for merge |
| Module repository integrity | `validate_manifests.py` plus unit tests of the gate on fixtures | Module repository CI | CI |
| Agent-side convenience | The same gate scripts exposed as `uv run` scripts in skills; personas; review lenses via `review_guidance` and `persistent_facts` | BMAD module | Advisory only |
| Loop-time gate | `[verify] commands` calling the repository gate | Consuming project's `.bmad-loop/policy.toml` | bmad-loop, if adopted |

The v7 alpha status sets the risk ordering of these pieces. The README says "V7 is in preview alpha on this branch: its skills, install path, and docs change often", with a release ETA of mid-November 2026, and recommends it only for "solo or small teams that can pivot"; the CHANGELOG lists breaking changes and calls Toolsmith "a first draft for v7" ([README](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/README.md), [CHANGELOG](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/CHANGELOG.md)). Ten commits have touched the module-format files since the records landed, the validator moved from `tools/` to `skills/bmad/scripts/` on 2026-09-29, and CIS's workflow still points at the old path, which now returns 404. Third parties already pin unreleased cores (TEA requires `6.13.0-next`). The riskiest dependencies for this module are therefore `doc-templates` and `bmad-facilitate`, which landed on 2026-11-04 and are the newest, least-settled part of `main`, followed by any bmad-loop integration, an early beta tied to a ticket-tree mode its own README calls experimental. The manifest keys are medium risk: `validate_manifests.py` run from the release tag detects drift cheaply. The least exposed pieces are the `SKILL.md` files and `uv run` scripts, which are ordinary agent-skill content, and the CI gate, which does not touch BMAD at all. The pin `version = "6.13.0"` for `bmad` is safe with today's `-next` build and with the final release, because setup special-cases an installed `6.13.0-next` against a minimum of exactly `6.13.0`; any other prerelease label would read as outdated ([`requirement_state`](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/skills/bmad/scripts/setup.py)).

## Reconciling the new goal with the earlier recommendation

The earlier recommendation had five elements: structured YAML requirement records with ModSpec-style `/req/<class>/<name>` identifiers; enforcement in CI instead of in tools that cannot provide it; OpenSpec demoted to an optional, replaceable proposal workflow; BMAD used narrowly as a core-only install pinned at stable v6.12.4, for review lenses, elicitation and party-mode personas; and a decision on OGC submission left to the project owner. The owner has now decided that OGC submission is a goal, alongside agentic spec-anchored development. I handle each element explicitly.

The first two elements are strengthened, not changed. With OGC settled, the structured-records default is no longer a hedge: ModSpec requires per-requirement identity, class membership and a paired abstract test, the only thing in the surveyed tooling that provides that is data the project owns, and the quality evidence favours schema-constrained records plus reference-resolving checks. The proposal's "strict validation pipeline" is the earlier "CI validation" with a better-informed rule set; the corrected pipeline simply moves out of the manifest. One decision remains open and I do not settle it: whether the YAML or the AsciiDoc is the source of truth. OGC practice is hand-written AsciiDoc, Metanorma documents the YAML route, and no examined OGC repository uses it. The earlier default (YAML) remains the better fit for agent authoring, per the evidence above, but a short spike should confirm that a data2text-generated requirement compiles cleanly and that the SWG and OGC editors accept a generated-block repository before the project commits; if they do not, the fallback is AsciiDoc as source with the same CI checks run against the semantic XML.

The third element is unaffected, with one update. OpenSpec stays optional. On `main`, `bmad-spec` and related planning skills are replaced by the Product Owner agent Sofia and a ticket tree, so the earlier advice to "skip `bmad-spec`" is moot there; the point it served, that a derived spec file hand-edited by humans is overwritten, should be re-checked against whatever v7 ships for specification documents.

The fourth element is where a real conflict arises, and the evidence supports staging rather than a silent override in either direction. The earlier report advised a core-only install pinned at v6.12.4, a line that is "frozen aside from bug fixes", and noted that skill-name overrides would face a v7 migration. A `bmod.toml` module exists only on v7 `main`. On v6.12 the custom-module route is `npx bmad-method install --custom-source` with the BMad Builder module, a different flow ([add-modules.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/docs/customize/add-modules.md)). There are two defensible paths. Staying on v6.12.4 keeps the earlier recommendation intact: write the standards skills and review lenses as repository-local content, not a packaged module, and accept a migration at the v7 cut. Adopting v7 `main` gets the module and Toolsmith now and accepts breaking changes before beta. The stage-gated recommendation is to build everything that is not BMAD-specific first (records schema, gate, Metanorma pipeline, skill instruction text, scripts), because that work is portable and carries most of the standard's actual quality control, and to package the thin `bmod.toml` layer only after v7 reaches a release that passes `validate_manifests.py` unchanged. The build order costs nothing if v7 slips, and the work is reusable if it ships. If the owner prefers to prototype the module on `main` now, that is reasonable for a solo or small team, which is the audience the README names, provided the module repository's CI pins and re-runs the validator against each BMAD change.

The fifth element, "BMAD only for review lenses", should widen modestly, and I flag that as a change. The earlier scope was review and elicitation; the new goal is agentic development of normative text. The IETF precedent (drafts that go "under your name", reviews that produce findings) and the quality studies support letting agents draft schema-constrained records and propose test cases, but not letting them commit, mint identifiers or declare conformance. The human-in-the-loop commit gate that results is: an agent drafts a record; the CI gate and review lenses run; a named human reads and commits, with the agent identified in a commit trailer; Naming Authority submissions, SWG votes and the OAB review remain human and institutional. This also answers the cautions from spec-driven-development practitioners that approval "does not establish that the requirements were right" ([Verdent guide](https://www.verdent.ai/guides/agents/kiro-spec-driven-development), practitioner source), which bites harder for standards because no downstream test suite exists until the abstract test suite is written.

## Corrected module skeleton, bmod.toml and block template

The skeleton below follows the documented multi-skill layout ([distribute-your-module.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/docs/toolsmith/distribute-your-module.md), [modules.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6/docs/toolsmith/modules.md)). Skill names carry the module code as a prefix (`bmad-` is reserved for the bmad-code-org), the record folder is `bmod-<code>`, and every `help/*.md` topic must be named in backticks in `help.md`.

```
module-repo/
  skills/
    bmod-ogcspec/                 # the module record
      SKILL.md                    # fixed redirect text; never invoked
      bmod.toml                   # the manifest below
      roster.toml                 # optional: [[members]] personas (not exercised in my test)
      help/help.md                # required; read by the bmad help skill
      doc-templates/              # optional: template:-frontmatter docs for bmad-facilitate (newest, riskiest)
    ogcspec-modspec/              # drafts records and tests from r7 text
      SKILL.md   bmod.toml   scripts/modspec.py   references/modspec-r7-rules.md
    ogcspec-metanorma/            # renders and compiles; calls the repo's pinned image
      SKILL.md   bmod.toml   scripts/metanorma.py
    ogcspec-gate/                 # runs the same checks CI runs and prints JSON findings
      SKILL.md   bmod.toml   scripts/gate.py
  README.md   LICENSE
  .github/workflows/module-quality.yml   # validate_manifests.py plus gate unit tests on fixtures
standard-repo/                    # separate: authoritative, BMAD-independent
  records/*.yaml  schema/*.json  sections/*.adoc  requirements/  abstract_tests/
  tools/gate/                     # schema, linkage, reference-resolution, log/XML checks
  .github/workflows/standard-ci.yml   # gate, then pinned metanorma compile; required for merge
```

The manifest below uses only keys verified in `setup.py`, `validate_manifests.py` and `module-files.md`, with no custom tables and no `description`. I wrote it into a scratch repository with placeholder skills and ran BMAD's `validate_manifests.py` from the pinned `main` commit; it reported "bmod files valid: 3 skills, 1 module records, 1 knowledge documents". That test did not exercise the script files, `doc-templates/` or `roster.toml`, and `update_source` is a placeholder. Policy knobs such as the base URI and severity threshold are free-text config answers; whether they belong there or in a project-owned file outside the manifest is a design choice (the gate in the standard's repository should read its own configuration, since it cannot depend on BMAD).

```toml
# skills/bmod-ogcspec/bmod.toml
[bmod]
code = "ogcspec"
version = "0.1.0"
update_source = "github:YOUR-ORG/YOUR-REPO/skills"   # placeholder; must start github:, https://, file: or plugin:
skills = ["ogcspec-modspec", "ogcspec-metanorma", "ogcspec-gate"]
required_skills = [
  { skill = "bmad", version = "6.13.0", source = "github:bmad-code-org/BMAD-METHOD/skills" },
]
recommended_skills = [
  { skill = "bmad-review", source = "github:bmad-code-org/BMAD-METHOD/skills" },
]
pre_install_message = ""          # both message keys are required by the validator
post_install_message = """OGC spec module installed. It needs uv, plus either Docker or the Metanorma CLI.
The authoritative checks live in your repo's CI; these skills call the same scripts."""

[[bmod.config_questions]]          # only key, prompt, default, scope are allowed
key = "metanorma_flavor"
prompt = "Metanorma flavor to compile with (leave as ogc for an OGC submission)"
default = "ogc"

[[bmod.config_questions]]
key = "ogc_doctype"
prompt = "OGC doctype attribute (standard, community-standard, best-practice, ...)"
default = "standard"

[[bmod.config_questions]]
key = "spec_base_uri"
prompt = "Draft spec base URI; keep the value unregistered-draft until the OGC Naming Authority accepts a name"
default = "unregistered-draft"

[[bmod.config_questions]]
key = "max_log_severity"
prompt = "Fail the gate on Metanorma log messages at this severity or lower (0 aborts; 1 serious; 2 less critical)"
default = "2"
scope = "team"
```

```toml
# skills/ogcspec-modspec/bmod.toml  (one per member skill)
[skill]
bmod = "bmod-ogcspec"
source = "github:YOUR-ORG/YOUR-REPO/skills"   # must equal update_source
scripts = ["scripts/modspec.py"]              # installed to _bmad/ogcspec/scripts/; must start with scripts/
```

Skills read an answer at run time with `uv run {project-root}/_bmad/scripts/resolve_config.py --project-root {project-root} --key modules.ogcspec.ogc_doctype`. For the agent's block template, the typed form below is assembled from the Metanorma documentation and real CS API sources; it has not been compiled. It deliberately does not choose between `http://` and `https://` for the spec base, because CS API (2025) uses `http` while r7 (2026) uses `https`, and neither source settles which a new standard should use.

```asciidoc
[requirement,model=ogc]
====
[%metadata]
identifier:: /req/<class>/<name>
part:: The server SHALL ...
====

[requirements_class]
====
[%metadata]
identifier:: /req/<class>
subject:: <target type>
inherit:: /req/<other-class>
requirement:: /req/<class>/<name>
====

[abstract_test]
====
[%metadata]
identifier:: /conf/<class>/<name>
target:: /req/<class>/<name>
test-purpose:: Verify that ...
test-method::
step::: ...
====

[conformance_class]
====
[%metadata]
identifier:: /conf/<class>
target:: /req/<class>
conformance-test:: /conf/<class>/<name>
====
```

In the standard's CI, the gate step should invoke `metanorma compile --agree-to-terms -t ogc -x xml,html,pdf <file>.adoc` from a pinned Docker tag, then fail on any severity 0 or 1 message and any `MODSPEC_*` message whose subject is a requirement, class or test, while exempting recommendations and permissions. Which AsciiDoc attributes the OGC flavor requires (`:doctype:`, `:committee:`, `:workgroup:`, `:status:`) is covered by the flavor's own validators, whose messages are all severity 2, so the severity threshold, not the exit code, decides whether a malformed header blocks the merge ([metanorma-ogc log.rb](https://github.com/metanorma/metanorma-ogc/blob/main/lib/metanorma/ogc/log.rb)). A cheap calibration step, which is my suggestion and untested, is to run the gate over the published `ogc-modspec` and CS API sources as known-good fixtures and confirm it produces no findings on them.

## Conclusion

The proposal's value is in its two role decompositions and its instinct to gate, not in its manifest. A `bmod.toml` is a packaging file: it can ship skills, pin other skills, ask free-text questions and print messages, and it cannot run, require or enforce anything outside BMAD's own setup. The fact that the proposal invented a plausible-looking configuration surface for BMAD and for ModSpec, and was wrong about the ModSpec rule it wanted to enforce, is itself the strongest argument for the architecture the evidence supports: the agent's instructions must be grounded on retrieved r7 text, and every rule must be a deterministic check that is itself tested against known-good OGC sources, because an LLM-authored linter inherits the same blind spots as an LLM-authored requirement.

The second implication is about sequencing and ownership. Everything BMAD-independent (records, gate, Metanorma pipeline, skill instructions) is portable and lets the project start immediately, while the BMAD packaging waits on a v7 release expected within weeks and on the one genuinely unresolved design question, YAML versus AsciiDoc as the source of truth. Neither the earlier recommendation nor the new idea is overridden: the structured-records-and-CI core is kept and sharpened, and BMAD's role widens from review lenses to drafting under a human gate, with identifier minting and Naming Authority submission left to people.
